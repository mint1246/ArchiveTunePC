# Android and shared-module inventory for SDK migration

## Scope and status

Static source inventory of the starting checkout, not a certification of behavior. Rows are updated as extraction proceeds; the Android API-level upgrade is a separate concern. The `gmsMobileUniversalDebug` compile and unit suite have since passed, but device and cross-variant behavior remain unverified. See `SDK_MIGRATION.md` for current milestones and results.

At the starting commit, `settings.gradle.kts` included `:app` and multiple shared JVM projects but no dedicated SDK project. The root `shared/` visible in this checkout contains build output, not an included source module. Several experimental SDK modules have since been added; inclusion alone is not evidence of a stable, versioned SDK API. `iosApp/` is not included in the Gradle settings inspected here.

## Build and runtime boundary

- `app/build.gradle.kts`: Android application, Kotlin/Compose, Hilt and KSP; compile SDK 37 minor 2, target SDK 37, minimum 26 (automotive 28); version 15.1.0 / code 151. Android is not a thin SDK host: application behavior, persistence, player, and presentation are substantially implemented under `app/src/main/kotlin/moe/rukamori/archivetune/`.
- Flavor dimensions are distribution (`gms`, `foss`), device (`mobile`, `tv`, `automotive`) and ABI (`universal`, `arm64`, `armeabi`, `x86`, `x86_64`); build types include debug, release and nightly. Variant source sets and manifests must be included in migration validation, not just `main`.
- App direct project dependencies include `:core`, `:moriextractor`, `:stream-resolver`, seven lyrics providers (KuGou, LRCLIB, SimpMusic, Paxsenix, BetterLyrics, Unison, YouLyPlus), `:lastfm`, `:canvas`, `:shazamkit`, `:spotifycore`, `:morideobfuscator`, and the extracted SDK modules (`:playback-core`, `:android-playback`, `:audio-analysis-sdk`, `:statistics-sdk`, `:account-sdk`, `:social-sdk`, `:social-realtime`, `:social-session`, `:social-login`, `:discovery-sdk`, `:download-sdk`, `:equalizer-sdk`, `:local-media-sdk`, `:lyrics-sdk`, `:lyrics-timeline`, `:playlist-import-sdk`, `:playlist-sdk`, `:backup-sdk`, `:chords-sdk`, `:chord-neural-core`, `:sponsorblock-core`, `:stems-sdk`, `:update-sdk`, `:together-sdk`, and `:together-transport`).
- `app` uses Media3/ExoPlayer, Media3 sessions and HLS, Room with checked-in schemas, DataStore, WorkManager, Hilt, Ktor and ONNX Runtime Android. Cast dependency is GMS-only. ONNX runtime dependency differs for arm64 vs the other ABI flavors; Android model execution cannot be assumed portable merely because its algorithms are Kotlin.
- `app/src/main/AndroidManifest.xml` declares media, microphone, notification, foreground-service and other permissions and Android components; device/distribution manifests add variant-specific behavior. Lifecycle, permissions, media sessions and services must remain platform adapters even if domain logic moves.

## Shared projects and portability

| Project | Evidence / role | SDK implication |
|---|---|---|
| `:core` | `core/build.gradle.kts`, `core/src/main/.../innertube/`: YouTube client, response models and page parsers | Kotlin/JVM project and Git submodule. Shared today across consumers, but not demonstrated as Kotlin Multiplatform or a stable public SDK. Audit global state, network configuration, serialization and account isolation. |
| `:moriextractor`, `:morideobfuscator` | Direct app dependencies and separate Git submodules; `morideobfuscator/jvm` is separately included | Inspect native/runtime and transitive requirements, licensing and platform compatibility before moving across an SDK boundary. |
| `:stream-resolver` | Kotlin/JVM; `PlaybackStreamResolver.kt`, `YtDlpStreamResolver.kt`, `YtDlpProcess.kt`; direct app dependency | Interface and implementations share a module; process-based implementations cannot be assumed available on Android or iOS. Verify the actual Android call path and packaging. |
| `:playback-core` & `:android-playback` | Kotlin/JVM (`playback-core`) and Android AAR (`android-playback`); direct app dependencies | `playback-core` provides `PlaybackController`, `PlaybackSessionHost`, `ClickedItemQueuePolicy`, crossfade gains, sleep timer, output-device, reorder and resumption policies; `android-playback` provides `Media3PlaybackController`, `AndroidPlaybackQueueStore`, `createMedia3PlaybackSession`, deferred source loading and Media3 state/queue adapters. |
| `:lyrics:http`, `:lyrics:*` | Provider projects in `lyrics/`, a Git submodule; `:lyrics:spicylyrics` is included but not a direct app dependency | Kotlin/JVM clients, not evidence of common/native support. Audit provider APIs, licensing, fallback and transitive dependencies individually. |
| `:spotifycore`, `:lastfm`, `:canvas`, `:shazamkit` | Kotlin/JVM projects directly used by app | Service-specific clients, not an aggregate SDK. Check credentials, API limitations, dependencies and platform transport before extraction. |
| Desktop modules | `:desktop-backend`, `:desktop-playback`, `:desktop-settings`, etc. in settings | Desktop implementations are not Android SDK dependencies. They may inform contracts but must not be assumed portable or Android-equivalent. |

The inspected shared builds use the Kotlin JVM plugin, not a multiplatform plugin. Kotlin/JVM reuse between Android and desktop does not imply iOS/native compatibility. A migration needs an explicit target matrix and dependency/ABI audit before choosing module boundaries. Git submodules have independent histories; a parent pointer alone does not contain their source changes.

## Verification inventory and gaps

- Existing local unit tests in `app/src/test/` cover selected policies and models: playback handoff/output/recovery/chunking, lyrics timelines/cache/adapters, statistics tracker, stems/DSP/model storage, chords, playlist import resolution, social, and Together protocol/permissions. Shared modules including `core`, `playback-core`, and `stream-resolver` have test source sets. Test names are evidence of coverage intent, not proof that tests passed or cover complete user flows.
- No `app/src/androidTest` files were found in this checkout. This is not proof that no external, manual, or CI device tests exist. Inventory CI and external test procedures separately.
- Before declaring a migration complete, establish a baseline and compare old/new behavior on actual devices: account sign-in and session refresh; browse/search and clicked-song identity; streaming, offline and downloaded playback; focus, Bluetooth and process recreation; foreground services and notification controls; library/playlist database upgrades; lyrics and chord timing; real stem audio; statistics; party interop; and platform-specific integrations.
- Exercise representative distribution, device and ABI variants, especially GMS/FOSS, mobile/TV/automotive, arm64 accelerated runtime and universal/non-arm64 runtime. Verify API 26 and automotive minimum plus current target behavior, permissions, release shrinking, model packaging, and network/auth failure modes. This is a proposed verification matrix, not a claim all combinations are supported or tested.
- Inspect dependency graphs and actual call sites per feature before deleting old paths; document stable SDK contracts, state ownership, concurrency/cancellation, error mapping, storage migration, secrets and compatibility. Run affected unit tests, integration/device tests and real packaged-app smoke tests; record commands, versions and results. See `SDK_MIGRATION.md` for executed tests and remaining verification gaps.
