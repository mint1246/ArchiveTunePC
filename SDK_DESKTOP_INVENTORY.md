# Desktop SDK migration inventory

## Scope and status

Source/build inventory of the baseline desktop tree, updated as SDK extraction proceeds. It does not claim migration completion or end-to-end feature parity. Paths are repository-relative; see `SDK_MIGRATION.md` for current changes and executed verification.

`settings.gradle.kts` includes desktop composition/UI (`:desktopApp`), desktop feature modules, `:playback-core`, `:stream-resolver`, `:core`, service/provider projects and platform integration modules. These are Gradle projects, not proof of a published/versioned SDK. Desktop uses Kotlin/JVM 21; the production packaging/native-image constraints in root `AGENTS.md` remain relevant to any extraction.

## Existing shared boundary and honest coverage

- `:playback-core` exposes neutral playback API/models/queue contracts and next-track prefetching; `:desktop-playback` supplies VLCJ. Both publish experimental local artifacts. `LatestLoadJobOwner` remains an internal desktop playback implementation.
- `:stream-resolver` exposes pure-JVM client/format/URL/header/expiry policy. `PlaybackStreamResolverTest` and `DesktopStreamResolutionPolicyTest` source files indicate regression intent, not that they passed in this audit.
- `:core` holds shared YouTube models/parsing/client behavior. `desktop-backend` is desktop-specific orchestration around that shared logic.
- Service projects (`:spotifycore`, `:lastfm`, `:canvas`, lyrics providers) are reusable clients with separate APIs, not one desktop SDK. Provider presence does not prove it is wired or feature-complete.
- Test source sets are present across key modules. Focused tests, a headless VLC run and a quick Native Image compile have since been executed; see `SDK_MIGRATION.md`. The full Windows desktop suite passed after its Linux-path test was made host-path-portable; actual Linux runtime behavior remains unverified. A module boundary or test name is not evidence of end-to-end correctness.
- Persistent data and secret handling are deliberately host-specific in several places: DPAPI auth, app-data settings/cache/index/statistics, download journal/files, and native helper/runtime paths. Any SDK contract must specify which host owns paths, encryption, lifecycle, cancellation, account isolation and migrations.

## Extracted desktop stream-resolution policy

The pure decision functions previously in `desktop-backend/src/main/kotlin/moe/rukamori/archivetune/innertube/DesktopStreamResolutionPolicy.kt` (`DesktopStreamResolutionMode`, `configuredDesktopStreamResolutionMode`, `resolveDesktopStream`, `allowsDirectAudioFastPath` and `directAudioFastPathUrl`) now live in `:stream-resolver` (`moe.rukamori.archivetune.stream.DesktopStreamResolutionPolicy.kt`) with focused JUnit 5 tests, while HTTP clients, `yt-dlp` process management and credential/runtime access remain in `desktop-backend` and `desktop-auth`. `desktop-stems` also shares gain sanitization with `:stems-sdk`.

## Verification still required for an SDK claim

Continue inspecting actual dependency graphs and call sites; establish contract tests for auth and account scoping, cancellation and thread ownership, stream identity/expiry, persistent format migration, secret redaction, and error mapping. Validate JVM consumers and any intended Native Image packaging separately; if Android or Native consumers are targets, verify toolchain/ABI and runtime compatibility instead of inferring portability from Kotlin/JVM reuse. Record executed commands and results before marking an area migrated.
